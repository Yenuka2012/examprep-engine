# M2.2-S2 — Isolated owner vault lifecycle and synthetic browser harness

**Status:** Implementation candidate in draft PR — NOT integrated, merged, or deployed.  
**Tracking:** #89, #87, PR #88, ADR-002 / PR #81, ADR-003 / PR #84, M2.1 / PR #86, release acceptance #83.

## Deployment boundary

The new `src/vault/OwnerVaultGate.tsx` is **never imported** by the production `src/App.tsx`, `src/main.tsx` or `index.html`. The synthetic harness HTML is built only through the explicitly different `vite.vault.config.ts` and output directory `dist-vault-test/`. It is **not** included in the production GitHub Pages `dist/` artifact; no public production "login" has been added.

`npm run test:e2e:vault` builds the test harness and launches it at `http://127.0.0.1:4174/vault-harness.html`, a separate secure-context localhost origin distinct from `github.io`. This synthetic-only build is a CI test artifact and **must never be deployed as a product interface**.

## Implemented

- **Enrollment:** requires independent master and recovery secrets, cryptographically creates a nonextractable in-memory DEK, and atomically writes the encrypted key-check verifier and vault header into a separate `examprep-secure-vault-v1` IndexedDB. An existing header or records blocks re-enrollment; no automatic overwrite.
- **Owner unlock:** obtains an exclusive origin-wide Web Lock, unwraps a key under master/recovery AES-KW, decrypts an authenticated internal verification record, validates vault identity/challenge/purpose, then creates a live owner session. Wrong secrets or damaged verifier fail closed; no app UI is displayed until unlock.
- **Exclusive access:** the owner Web Lock spans the entire unlocked session. Without the lock or live key, reads and writes fail closed. Multiple tabs cannot both own the vault. This is local *cryptographic unlock*, **not server authentication** and not tenant RBAC.
- **Persistence:** reads and writes operate on encrypted records. Writes require a valid current session, key, exclusive Web Lock and vault-header consistency. Create-only rejects duplicate IDs. Updating an existing record requires its previous authenticated random nonce and checks the prior ciphertext/key before an IndexedDB atomic compare-and-swap. Crypto operations run **outside** active IndexedDB transactions to prevent Safari's auto-commit issue.
- **Lock:** explicit Lock, a five-minute inactivity check, `visibilitychange` hidden, `pagehide` and foreground time checks trigger locking. New operations stop; accepted writes are drained with `Promise.allSettled`, then key references are released and decrypted UI state is cleared. Browser process crashes can still interrupt an in-flight save; this is **not** a guarantee of durable completion in a crash.
- **Synthetic UI:** Manage Content and Exam Practice are just workspace choices for the sole owner. The only content in the harness is a synthetic private note to demonstrate encrypted save/read. No production bank/attempt records are imported.
- **Browser tests:** Playwright Chrome, desktop Safari/WebKit, iPhone WebKit and iPad WebKit emulations cover enrolment, encrypted-only IndexedDB and Web Storage absence, recovery unlock after reload, wrong passphrase, ciphertext tampering, stale update rejection, competing tabs and short-idle auto-lock. Synthetic test-only query overrides are excluded from the production product.

## Remaining security gaps before production

1. **No existing data migration.** Current v0.3.0 `examprep-v1` banks, attempts, active sessions and catalog are still plaintext IndexedDB; no migration/deletion code has been added. User's encrypted logical-v2 backup must be exported **and independently restored** before any migration, with the active-exam policy resolved.
2. **No crash-resumable import or verified encrypted-vault backup.** The experimental new DB must support a versioned portable encrypted-vault export, fresh-origin restoration, schema validation, relation integrity and recovery rehearsals. Do not treat a browser IDB transaction as proof of recoverability after device loss.
3. **No physical iPhone/iPad Safari sign-off.** Playwright emulation cannot certify iPadOS PWA storage, Split View, suspension/background behavior, file handling or WebAuthn PRF support. Physical devices remain a release gate.
4. **No trustworthy rollback-proof record revisions.** Random nonces plus transaction compare-and-swap prevent accidental stale writes **in one live database**, but cannot detect an attacker replaying entire valid prior snapshots without an external monotonic trusted state.
5. **No production integrated exam state.** Need invariant-preserving adapter for full bank/attempt/session/catalog writes, input validation, immutable published syllabi, cross-tab exam ownership, end-of-exam durable saves, unlock UI state, save error feedback and safe auto-lock of an in-progress exam.
6. **No true server-side authentication.** GitHub Pages remains a public app shell. Ubuntu Level A would add VPN/network isolation; Level B authentication is a separate optional architecture milestone.
7. **Key/secret handling:** Web Crypto nonextractable key and clearing application references do not protect against malicious same-origin JavaScript while unlocked or guarantee physical memory zeroization. Master/recovery credentials must be high entropy; JS length checks do not prevent offline password guessing.
8. **Browser lifecycle race analysis:** concurrent lock/save/unload, stale UI references, asynchronous cleanup and storage quota/eviction require further adversarial review. This prototype is not a production acceptance declaration.

## CI requirements

The integrated GitHub Actions pipeline adds `vault-synthetic-browser-tests` using the existing digest-pinned Playwright image, and Pages deployment is conditioned on that job alongside unchanged verify/browser/CodeQL jobs. CI builds the test harness *separately* from normal Pages production output. Both independent and integrated E2E workflows remain intact.

**No merge or production migration until:** final-head integrated test suite + new synthetic E2E + independent browser E2E + CodeQL pass, the earlier ADRs and M2.1 are reconciled, owner restore/physical-device acceptance #83 is complete, and secure migration/recovery is explicitly approved.
