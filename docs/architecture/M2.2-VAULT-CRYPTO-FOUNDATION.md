# M2.2-S1 — Isolated encrypted-vault cryptographic foundation

**Status:** Experimental / draft PR. **Date:** 2026-11-07. **Tracking:** #87; vault ADR-002 in #81; dual-host ADR-003 in #84; porting #86; production acceptance #83.

## Exact implementation boundary

This work adds **new, unreferenced modules** at `src/vault/crypto.ts` and `src/vault/storage.ts`. The public application `src/App.tsx`, `src/db.ts`, existing backup envelope and all production data stay unchanged. The standalone encrypted store `examprep-secure-vault-v1` is created only when `ExperimentalVaultRepository.setup()` is explicitly called. Current production IndexedDB `examprep-v1` is **still plaintext at rest**. No client-only sign-in claims server authentication.

### Key and record design

- Generate a fresh, randomly generated **AES-256-GCM 256-bit data-encryption key** (DEK). Temporarily allow extractability solely to wrap it under two different derived AES-256-KW keys; subsequently hold only a **nonextractable** Web Crypto DEK for normal runtime operations. JavaScript memory sanitization is best effort, not a security boundary against hostile active-origin JavaScript.
- Independently salt (16 random bytes each) the master credential and the separate **recovery credential**, with **PBKDF2-HMAC-SHA-256, 600,000 iterations** for native browser portability. Format and iteration count are version-checked. Argon2id remains an explicit compatibility-reviewed future option, not silently assumed supported.
- Key wrapping uses AES-KW for the 256-bit DEK; wrapped bytes, derivation settings and random vault identifier appear in the versioned vault header. Neither raw DEK nor credentials are persisted. **Credential entropy** is a human responsibility: length checks alone do not prevent offline guessing; use password-manager-generated randomness.
- Each encrypted JSON record has an **opaque random UUID** and a freshly generated **96-bit AES-GCM nonce**, with authenticated additional data (AAD) binding `format`, `vaultId`, `recordId`, `recordType`. Only the opaque ID, record type and cipher envelope are IndexedDB keys/values, and sensitive source identifiers and question details must be contained *inside ciphertext*.
- AES-GCM detects tampering and swapped metadata; it **does not** detect valid older snapshots of entire encrypted records (rollback) or deletion by a local adversary without trusted external monotonic state.
- Fail closed on unknown envelope versions/fields, malformed/oversized base64, invalid nonces, wrong vault identity, invalid wraps or wrong credentials. Record plaintext size is bounded at 8 MiB pending chunked backup/large bank design; 8 MiB is not a complete solution for large exam histories.
- No CSP changes, new NPM dependencies, cloud services or private keys in Git.

### Prototype API contract

`createVault(masterSecret,recoverySecret)` returns `{header,key}`. `unlockVault(header,secret,'master'|'recovery')` unwraps a nonextractable in-memory key. `encryptVaultRecord(header,key,recordType,value,optionalRecordId)` outputs a versioned AES-GCM envelope. `decryptVaultRecord(header,key,envelope)` authenticates AAD and decrypts JSON.

`ExperimentalVaultRepository` offers `setup`, `header`, `unlock`, `put`, `get` and `encryptedRecords`. It creates a **separate** IndexedDB database and never alters the production Dexie database. This is not yet production persistence: write key possession, cross-tab concurrency, rollback/replay semantics, migration journals, validators and lock lifecycle require further engineering.

## Threat model and explicit outstanding work

| Threat / requirement | This phase | Remaining gate |
| --- | --- | --- |
| Theft of locked encrypted record dump | AES-GCM with DEK and PBKDF2-derived wrapped key | Strong secrets, side-channel review, browser testing |
| Metadata/ciphertext manipulation | AES-GCM authenticated AAD, strict validation | Whole-database rollback resistance is not supplied |
| Wrong passphrase / recovery | Fail-closed key unwrap | Credential enrollment, secure recovery UX |
| Cross-tab race / stale writes | **Not solved** | Origin-wide Web Locks, atomic write and compare-and-swap revision protocol |
| UI data exposure | **Not solved** | Unlock and inactivity locking, cleared React state, key lifecycle |
| Active exam continuity / persistence | **Not solved** | Durable final writes and recovery-compatible exam state |
| Production plaintext IndexedDB migration | **Not attempted** | Independent full encrypted backup, journal, read-back proof, explicit destructive cleanup approval |
| Host/cross-device portability | Not integrated | GitHub Pages and Ubuntu adapters with isolated origins; user-exported encrypted backup |
| Physical Safari devices | **Not tested** | Mac, iPhone and iPadOS Safari/Home Screen PWA + background/restore |
| Server-side login | Out of scope | Future Ubuntu Level B separate authenticated backend design |

## Automated test criteria

Unit tests cover independent wraps, correct master/recovery unlock, wrong credential rejection, nonextractable runtime key, plaintext absence from serialized envelopes, fresh nonces, authenticated record IDs/types, cross-vault rejection, malformed salt/wrap/nonce/ciphertext/version, and input-size bounds.

**Do not integrate with the existing application or migrate personal content merely because unit, CodeQL and browser CI are green.** Before M2.2-S2, perform an independent cryptographic design review, harden encrypted repository write authentication/atomicity, add browser tests of a *separately hosted synthetic vault*, define versioned logical backup/recovery (including active exam policy), and confirm physical iPhone/iPad compatibility.
