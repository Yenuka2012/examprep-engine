# M2.8 — Encrypted-only examination runtime (synthetic-first)

**Status:** DRAFT / no production encrypted cutover. Tracks issue #122.

## Runtime boundary
The new `src/vault/encryptedExamRuntime.ts` provides a typed examination
persistence layer using only the verified S1–S3 `OwnerVaultSession` and
encrypted destination binding. It DOES NOT import `src/db.ts`, local plaintext
Dexie tables, localStorage passwords, network, or migration routines.
It is excluded from the GitHub Pages production import graph by the
existing 49-file security fence.

The API supports authenticated encrypted bank/certification/syllabus creation,
question-bank and historical attempt listing (including validated M2.7
converted encrypted source wrappers), single-slot exam creation, answer/flag
CAS autosave, secure resume, and idempotent submission.

## Crash-recovery protocol
The encrypted active slot has one **fixed opaque UUID**; all operations
use the authenticated owner's Web Lock and per-record nonce CAS, so an old
revision cannot overwrite new answers or start a second live examination.

Manual submission uses a staged encrypted intent:
1. Before submission, all user answers must be durably CAS-saved and the
   caller must present the exact latest encrypted slot revision. Unsaved
   state refuses submission rather than silently losing answers.
2. Atomically CAS-write a **preparing** slot with immutable validated exam
   snapshot, computed attempt, and randomly generated opaque attempt UUID.
3. Idempotently create the encrypted attempt using the persisted UUID.
   After a browser interruption, reopen the authenticated vault and
   independently verify an existing attempt against the prepared snapshot.
   A mismatched record fails closed without overwriting original data.
4. CAS-seal the slot as **complete** only after the encrypted attempt has
   been decrypted and reauthenticated. On restart, a remaining preparing
   intent is reconciled, not submitted a second time.
5. Start a next exam by CAS-replacing only the completed singleton slot.
   Previous encrypted attempts remain in separate immutable records.

The live original production \`examprep-v1\` question banks, attempts,
unfinished sessions and browser PWA are NOT opened or changed.

## Mandatory release blockers
This phase is a persistence component, not a complete encrypted React
exam UX or actual migration. It must be tested in the isolated localhost
vault harness with genuine Dexie ciphertext, real owner unlock and
recovery Web Locks, interrupted saves/submit, background redaction, and
Chromium/WebKit/iPhone/iPad emulation.

The M2.7 converter and M2.6 origin checker (#121/#119) remain separate
experimental drafts, not merged. Before encrypted-only deployment,
integrate the real Manage Content, Exam Practice, reporting and backup UI,
complete physical owner iPhone/iPad acceptance, verify genuine post-v0.3
logical-v2 backup and recovery, and verify isolated HTTPS destination
origin/no plaintext fallback (#100/#78/#83).

**No real owner migration, encrypted-at-rest production activation or
plaintext source cleanup has occurred.** Plaintext deletion is not
authorized by this engineering prototype.

### Additional reviewed integrity gates

- Starting an examination requires its complete, unchanged question bank
  to be present as authenticated encrypted vault content; matching a bank ID
  alone is insufficient. This blocks unsourced or modified exam snapshots.
- When reconciling a persisted preparing intent, the runtime scans existing
  encrypted attempts and refuses to append a duplicate logical examination
  under any different opaque record UUID. A collision is a recovery
  investigation, never permission to overwrite or delete ciphertext.
- Browser adversarial tests seed synthetic mismatch and duplicate conditions
  against real AES-GCM/IndexedDB vault storage, across Chromium, desktop
  WebKit, emulated iPhone, and emulated iPad.
