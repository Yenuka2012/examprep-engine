# M2.6 — Distinct-origin topology preflight (synthetic only)

**Status: REVIEW ONLY. No data migration, deployment, plaintext cleanup or owner-data access.**
Tracks [#118](https://github.com/Yenuka2012/examprep-engine/issues/118) and older
cutover blocker [#100](https://github.com/Yenuka2012/examprep-engine/issues/100).
Reference production: v0.3.2, SHA `1256a396c3efdbfd0f9565ccf48b896eb37a2b2d`.

## Architecture decision

The original Pages source is `https://yenuka2012.github.io/examprep-engine/`.
Its IndexedDB name is `examprep-v1`; production native Dexie 3 is
IndexedDB version 30. Cached historical JavaScript can still write existing
stores even if another tab takes an exclusive cooperative Web Lock or runs
an IndexedDB version upgrade. A newer schema is **not** an ACL.

A destination at a **different path on** `yenuka2012.github.io` shares the
browser origin and storage. It cannot isolate encrypted records from old
same-origin code. A separately controlled HTTPS hostname provides a real
origin boundary for new browser storage, but DOES NOT freeze, revoke or
protect the original plaintext source against stale writers. Even with
different hostnames and successful tests, no real migration is authorized.

## Pure implementation

`src/vault/originIsolation.ts` is isolated inside the existing
experimental vault directory. It has no imports of real production DB,
network, browser globals, IndexedDB, Web Locks, service workers or crypto.
It evaluates supplied URL strings only; all results say either:

- `BLOCKED` for same origin, same hostname/different port, HTTP/opaque,
  unsafe aliases, embedded credentials, query/hash, unsupported hosting model or invalid URL; or
- `TOPOLOGY_ONLY_PASS_NOT_AUTHORIZED` for two apparently distinct HTTPS
  hostnames. This is NOT a migration, hosting or TLS approval.

It returns only normalized origin strings (no paths, credentials or query).
A valid `https:` URL does not demonstrate DNS control, trusted TLS, VPN
isolation, backend hardening, CSP or application legitimacy. Manual checks
are mandatory for either public static Pages or private Ubuntu hosting.
A separate browser profile on the same origin is also an independent
storage container but is NOT equivalent to a cross-origin deployment.

## Owner recovery and cutover invariants

1. Complete any active examination **without forcing PWA refresh**; confirm
   the durable submitted attempt. Logical-v2 full backups do not contain
   unfinished sessions.
2. Export a fresh genuine logical-v2 authenticated encrypted backup from
   the original owner browser. Do not upload the backup, its passphrase,
   private question data, or restoration secrets into GitHub issues.
3. Restore **only into an empty separate browser profile**, confirm
   certifications, published/draft syllabi, question-bank IDs/counts and
   historical attempt counts/score snapshots. Never clear production data
   in order to create this empty profile.
4. Physically verify iPhone and iPad Safari/Home Screen PWA, offline
   reopen, background/foreground behavior, file export/import,
   landscape/portrait and iPad multitasking. Browser emulation does not
   satisfy real owner acceptance.
5. Inspect source quiescence and source/target manifests with existing
   ExamLock FIRST and exclusive legacy writer lock SECOND. Both locks
   cover only cooperating tabs; do not infer non-cooperating clients absent.
6. Obtain separate explicit authorization before a non-destructive copy,
   with a distinct destination origin, independently verified encrypted
   recovery, and no plaintext fallback. **Plaintext cleanup requires an
   additional subsequent explicit authorization.**

The project permanently supports (1) public GitHub Pages single-owner
offline-first PWA, and (2) future private Ubuntu VM HTTPS preferably VPN,
with one portable codebase. Static vault unlock is cryptographic local
access, not server authentication. No external paid infrastructure or new
dependencies are introduced.

source-barrier, vault/restore and CodeQL suites. Existing production source
