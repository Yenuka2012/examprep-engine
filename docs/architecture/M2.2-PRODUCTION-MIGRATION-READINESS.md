# M2.2-S5 — v0.3.0 production migration readiness (review-only)

**Status:** Candidate / draft PR, **no production migration**. **Baseline main:** `bcea4dc` / `v0.3.0` / Dexie v3. **Tracking:** #95; previous S4 #93 / PR #94 and S3 #91 / PR #92. **Date:** 2026-11-08.

## Actual production data architecture reviewed

`src/db.ts` defines the legacy **`examprep-v1`** Dexie database:
- `banks` keyed by `bank_id`
- `attempts` keyed by `id`, with frozen `questionSnapshots`, answers and `correctCount`
- `activeSessions` keyed by `current`, whose `value` contains an in-progress exam and frozen question bank
- `certifications` keyed by `id`
- `syllabusVersions` keyed by `certificationId/version`, draft revisions and immutable published entries

**Important:** current v0.3.0 full encrypted logical-v2 backups cover banks, attempts, certifications and syllabus versions, **but explicitly exclude `activeSessions`**. A validated user backup is insufficient to protect an unfinished exam. An open exam is therefore an absolute migration block unless a separate, independently rehearsed active-session migration/recovery procedure is approved.

**Historical attempts:** a bank can be deleted or replaced after an attempt is finished. The attempt's **frozen** `questionSnapshots` and score remain authoritative. Readiness validation must not require all historical `Attempt.bankId` values to have a currently imported bank; it must validate the answer keys, choice IDs and recompute `correctCount` from each attempt's snapshots. The catalog was introduced in M1.1, so an older bank may reference a certification that is not yet represented in the catalog—this is a reconciliation warning, not silent data deletion or a categorical migration failure.

## Legacy write-path coverage: source quiescence is NOT currently enforced

| Source write operation | Production code path | Existing protection | Required future production barrier |
| --- | --- | --- | --- |
| Question bank import/replace | `src/App.tsx` `importFile` → `db.banks.put` | Validated JSON + replace confirmation | Shared, exclusive migration/write coordination |
| Question bank delete | `src/App.tsx` `deleteBank` → `db.banks.delete` | UI action | Shared source writer barrier |
| Certification creation | `src/catalog.ts` `addCertification` | Add-only ID | Shared source writer barrier |
| Syllabus draft save | `src/catalog.ts` `saveSyllabusDraft` | Dexie transaction + optimistic revision | Shared source writer barrier; preserve revisions |
| Syllabus publish | `src/catalog.ts` `publishSyllabusVersion` | Dexie transaction + immutable published state | Shared source writer barrier |
| Active exam create/save/complete | `src/examPersistence.ts` | `examprep-active-exam-v1` Web Lock coordinated by `src/App.tsx`, durable save queue | Block active exams and coordinate full migration barrier; no final write loss |
| Backup merge restore | `src/recovery.ts` `restoreBackup` | Exam Web Lock + conflict-checking Dexie transaction | Shared source writer barrier as well; refuse while migration holds source |
| Encrypted full backup export | `src/App.tsx` `backup` | Reads stores; **no universal source write freeze** | Consistent snapshot under shared writer barrier for authoritative migration evidence |

**The experimental owner Web Lock `examprep-secure-vault-v1-owner` protects only the new isolated vault.** It does **not** stop the legacy source app from changing question banks, catalog entries or attempt/session records. Neither S4 nor this S5 introduces a production write barrier. Enabling a migration while ignoring these writers could silently create an inconsistent encrypted copy.

## What S5 actually implements

`src/vault/productionReadiness.ts` is a pure, data-only function that **does not import `src/db.ts`, open IndexedDB, contact a server, or call StorageManager**. Given a synthetic snapshot and caller-provided evidence and storage quota data, it emits a **non-sensitive aggregate report**:

- Five-store inventory and explicit bounded counts; duplicate and invalid IDs.
- Question bank schema via existing generated validator; historical attempt frozen-question/answer score consistency.
- In-progress exam detection; saved-exam structural validation; certification and syllabus references and published state validation.
- No leaking of question text, bank names, IDs or answer keys into findings. Findings use stable error codes, counts and conservative byte estimates.
- Explicit technical and **owner/evidence gate** blockers. Missing/unknown evidence or quota fails closed.
- `PRECHECK_PASS_NOT_AUTHORIZED` is deliberately **not production authorization** even if every caller-supplied boolean is true. Evidence is not cryptographically attested and the function alone cannot verify device sign-off, actual recovery, deployment controls or writer enforcement.

The storage screen accepts only caller-supplied `quotaBytes` and `usageBytes`; it requires at least **max(32 MiB, 3× serialized source + 8 MiB)** estimated free space. This conservative check is merely a *screen*: browser quotas can change, Safari can evict storage, source/encrypted/backup copies have different sizes, and no quota is reserved. A complete dry run with device-specific measurement and independent encrypted backup remains mandatory.

## Synthetic-only source writer freeze rehearsal

The fixture `examprep-synthetic-legacy-v1` now uses `examprep-synthetic-legacy-v1-write-barrier` Web Locks for its two **test-only** write entry points (`seedIfEmpty` and `modifySourceForTest`). A test-only exclusive freeze denies these writes until explicitly released. Browser tests check the denial and subsequent re-enablement, including emulated iPhone and iPad WebKit. The fixture timestamp was corrected to satisfy the actual `validateExamSession` expiry invariant.

This proves only that **synthetic cooperating writers** respect a shared lock. It does not imply `src/App.tsx`, `src/catalog.ts`, `src/recovery.ts`, or `src/examPersistence.ts` currently take the production lock. A separate PR must implement the production barrier, keep it during read + copy + final verification, add negative tests for every write path, and define a crash/restart response.

## Production cutover sequence (design; NOT authorized)

1. **Evidence collection:** reconcile v0.3.0 release issue #83; capture commit, production browser/OS versions, schema/counts, *post-v0.3.0* logical-v2 encrypted backup in an external safe location and independently verified clean-profile restoration of all exportable categories. Capture iPhone/iPad physical Safari+PWA acceptance and WebKit #76 RCA.
2. **Host/origin boundary:** choose a dedicated HTTPS origin for the encrypted vault; `/examprep-engine/` path on a shared github.io origin does not isolate IndexedDB. Keep Ubuntu VM Level A private behind trusted VPN/HTTPS. Browser profiles and host origins remain separate; migration needs explicit encrypted export/import.
3. **Freeze/write quiescence:** finish or preserve active exams with an independently tested procedure; introduce a **shared** source-wide migration/exam/bank/catalog/restore lock and a visible read-only mode. Acquire the source barrier *before* the read-consistent five-store source snapshot, hold it through final copy/integrity checks, and fail closed if lock unavailable, tab uncooperative or the source changes.
4. **Preflight:** strictly validate actual record schemas, historical attempts, catalog version relationships, quota, device support, source counts and size limits. Record only redacted totals and error codes in diagnostics. If any blocking finding remains, no migration proceeds.
5. **Non-destructive encrypted copy:** enroll a new vault, retain plaintext DB intact, record planned opaque IDs in encrypted journal, encrypt and verify every record, checkpoint after each durable write; support crash resume using recorded IDs and compare-and-swap.
6. **Authenticated recovery proof:** export an encrypted S3 transfer, independently restore into a fresh browser profile/origin, authenticate inventory, and compare record counts, frozen attempt scores and question-bank/certification/syllabus relationships. Preserve external backup and distinct recovery credential.
7. **Owner review:** clearly show what remains plaintext, the real encryption status, source and destination counts, current app/browser origin and externally stored backups. **A separate explicit owner authorization is required before any destructive plaintext cleanup.**
8. **Cleanup/rollback:** never call `indexedDB.deleteDatabase('examprep-v1')`, clear all site storage, remove origin caches indiscriminately, or downgrade from Dexie v3 to v2 as an automated fallback. After approved cleanup only, preserve the encrypted recovery build, verified backups and documented lost-device recovery.
