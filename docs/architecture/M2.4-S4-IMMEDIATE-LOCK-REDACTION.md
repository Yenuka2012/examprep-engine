## Verified issue and corrected contract

The experimental S2/S3 owner session originally invoked onLocked only **after**
`Promise.allSettled(pending)`. A slow in-flight AES-GCM or IndexedDB
save could leave decrypted React state visible during Safari pagehide/background
suspension. The new contract separates *security state* from *I/O durability*:

1. On first lock invocation synchronously set closing, discard the session's
   reference to its nonextractable DEK, cancel the idle timer and remove
   background listeners. Immediately invoke onLocked to clear all decrypted
   state via React flushSync. A synthetic CSS concealment applies during this
   transition. On callback failure, concealment stays in effect.
2. Deny **all new** saves, reads, exports, and touch calls. Already accepted
   async operations hold a captured key reference and settle under the still-
   exclusive owner Web Lock. The lock is **not** released until all accepted
   operations finish, including failed operations. No await occurs before
   the immediate redaction callback.
3. A late encrypted read is rejected once locking begins; the destination
   gate also invalidates its generation. All synthetic UI async completions
   compare their captured UI generation so late saves, exports and reads
   cannot restore private state or outdated error content.
4. onPendingFailure conveys a **sanitized** locked-state notification if an
   accepted operation or owner lock release fails. Callback exceptions
   cannot block lock release. The onReleaseSettled callback retains a
   warning if lock release failed. Programmatic browser pagehide/visibility
   callbacks catch lock promise rejection to prevent unhandled rejections.
5. Unlock controls remain unavailable while accepted operations are draining.
   Lock remains clickable even while a save is pending.

**Safety limitation:** A hung promise cannot safely be timed out by releasing
the owner Web Lock: that could permit a competing writer while the original
transaction still runs. Safari may suspend timers; browser force-kills can
interrupt durability. UI immediately hides content, but memory zeroization
or reliable cancellation of JavaScript strings/ongoing WebCrypto/IndexedDB
is not guaranteed. Recovery requires authentic ciphertext and separately
retained encrypted backups. Physical iPhone/iPad validation remains mandatory.
