## Why this is not an S4/S5 branch merge

Earlier S4/S5 branches still contain an S2 owner session and React gate
that redact decrypted state only *after* pending writes settle. Draft #109
corrects this timing and protects against stale async reads and UI completions.
Blindly cherry-picking or merging all S4/S5 files would silently reintroduce
that vulnerability. Therefore the integration:

- imports only the S4 encrypted journal and synthetic legacy implementation,
  pure S5 readiness analysis, and their prior Vitest/Playwright specifications;
- retains draft #109 owner session, owner lock, immediate React redaction,
  authenticated encrypted-only destination, clean recovery and all existing
  browser tests;
- extends the *current* cryptographic allowlist solely with the
  `migration-journal` record class; the current owner session gains
  authenticated `listByType` with a **post-await** lock-generation check;
- adds S4/S5 test-harness controls without importing the production
  `src/db.ts` or using the real `examprep-v1` source.

## Isolation and no-data-loss invariants

1. The only test source database name is
   `examprep-synthetic-legacy-v1`; its five-store payload is an artificial
   fixture, not the owner's exams. Production database name
   `examprep-v1` MUST NOT be opened by the experimental harness, journal,
   readiness checker, or test migration code.
2. A synthetic exclusive source Web Lock is acquired **by the migration
   function itself** before the consistent source snapshot and held through
   all journal plans, ciphertext copies, read-backs and final source
   fingerprint comparison. A contention failure must stop before modifying
   the destination. The lock is released in `finally`, including after
   interruption and AES-GCM failure.
3. This freeze only coordinates **cooperative synthetic test writers**.
   Older same-origin ExamPrep code can bypass Web Locks and native IndexedDB
   version upgrades. It is NOT a durable revocation mechanism or authority
   to copy/delete any production source records (issue #100).
4. A cryptographically authenticated migration journal is written before
   any destination ciphertext. Planned opaque UUIDs remain stable across
   retries; a crash after record save/before checkpoint resumes by checking
   that same record and its source payload digest. Already-copied content
   with mismatched or missing ciphertext fails closed; it is never
   overwritten or silently re-imported.
5. Validated journal state follows whole-copy read-back, source fingerprint
   recheck and an authenticated final journal read-back. Encrypted-vault
   export/clean-profile restore must independently verify all copied
   ciphertext and journal entries.
6. The pure S5 audit returns only aggregate counts and stable risk codes.
   Required owner backup, physical-device, origin isolation and migration
   authorizations are absent from the rehearsal, yielding `BLOCKED`.
   Even a hypothetical full-evidence technical result is explicitly named
   `PRECHECK_PASS_NOT_AUTHORIZED` and has NO migration side effect.
7. The synthetic fixture intentionally contains one active exam session
   to exercise complete journal copying. **This does not override** S5's
   real-world block on an unfinished exam; the user must finish and
   durably save real exams before any separately approved cutover.
8. The current data is STILL plaintext in production. Migration and deletion
   are separate explicit owner approvals. No automatic old-client cutoff,
   PWA cache invalidation, Web Lock timeout, Dexie downgrade, or browser
   storage cleanup is implemented.
