# M1.1 — Certification and syllabus catalog architecture

**Status:** feature branch / PR candidate; not yet in production.  
**Milestone:** M1 / version target v0.3.x.  
**Design principle:** no destructive changes to M0.1 browser data; no assumed official exam endorsement.

## 1. Requirements and scope
- Maintain local certification profiles (stable ID, name, provider).
- Maintain multiple syllabus versions for each profile; domain codes, names, weights (sum exactly 100%), and optional objectives.
- Allow draft revisions with optimistic concurrency; publish freezes the version. Corrections require creating a new version ID.
- Optionally link a public HTTPS source URL and source-review date for provenance.
- Show existing local question-bank coverage by exact certification ID + `syllabus_version` string match. Never rewrite imported banks or historical exam snapshots.
- Encrypt certification catalog content in individual matching-bank exports and full-profile backups.
- Explicitly distinguish reference domain weights from actual exam rules and official pass thresholds.

**Non-goals:** provider login, vendor endorsement, real official exam syllabi, bank schema breaking changes, scoring changes, adaptive practice, remote synchronization, and automatic official weighting in existing exams (UX-002 and EX-005).

## 2. Data model and migration
- Dexie database remains `examprep-v1`; add **schema version 3**.
- Existing tables: `banks`, `attempts`, `activeSessions` remain unchanged.
- Add `certifications` (primary key `id`).
- Add `syllabusVersions` (primary key `id=certificationId/version`; secondary `certificationId`, compound `[certificationId+version]`).
- A published version is immutable. Only draft writes are permitted via the catalog module, and each draft update must match the previous revision.
- Never infer certification IDs from names, rename existing profile IDs, or rewrite existing bank snapshots. Imported legacy banks remain usable with or without a matching catalog entry.

**Compatibility warning:** A browser that has opened the v3 schema should not be rolled back to the v2 application without an explicit compatibility check. Back up encrypted data before future schema changes; do not erase browser storage as a rollback step.

## 3. Validation and security invariants
- Identifiers are bounded safe-token strings and reject `__proto__`/`constructor`/`prototype`.
- Certification IDs are unique and append-only.
- Syllabus versions are uniquely keyed, 1–20 domains, all weights integers from 1–100 and total exactly 100%.
- Domain codes/names must be unique regardless of case; at most 20 objectives per domain, no duplicate objectives.
- String lengths, control characters, timestamps, HTTPS source references, and unknown properties are rejected by `validateCertification` / `validateSyllabus`.
- Publication and optimistic revision changes happen within IndexedDB transactions. A published version cannot be modified from the editor.
- Browser profile access remains a trust boundary: IndexedDB data is **not encrypted at rest**.
- Only synthetic/local data is used for CI testing; no copyrighted vendor question banks are bundled.

## 4. Backup and restore
- Authenticated AES-256-GCM envelope and PBKDF2-SHA256 iteration count remain the same.
- Logical backup v1 gains **optional** `certifications` and `syllabi` arrays. Older backups without the arrays remain accepted, and legacy tests must continue to pass.
- New whole-profile exports include both arrays. Matching individual-bank export includes its catalog profile/version when available.
- Validation limits: max 200 profiles, 500 versions per backup; every restored syllabus includes its parent profile in the same backup.
- Recovery uses **one** Dexie transaction for banks, attempts, profiles and versions; conflicts abort the transaction, identical records are retained.
- Active exam or second-tab Web Lock prevents restoration, preserving existing exam state.
- Same 64 MiB encrypted export/restore envelope limit applies.

## 5. Tests and release criteria
- Unit: unknown keys, bad IDs, bad weights, duplicate domains/objectives, bad dates/URLs, invalid publication, back-compat backup, encrypted catalog round trip, orphaned or conflicting records.
- Browser: add draft, publish, reload, exact-bank coverage, v2→v3 non-destructive upgrade, encrypted catalog export and fresh-profile restore in Chromium/WebKit.
- CI: typecheck, unit, dependency audit, production build, JS/Actions CodeQL, Chromium/WebKit browser suites.
- Manual: physical iOS Safari browse/create/reload/publish, production HTTPS and PWA upgrade without loss, encrypted full-backup restore in separate profile.
- **Do not merge** unless required PR gates and tests pass. **Do not claim production release** until deployed commit and live acceptance are recorded.
