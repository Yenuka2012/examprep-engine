# M2.2-S3 — Portable encrypted-vault recovery and gated migration design

**Status:** Candidate in draft PR, experimental / synthetic-only; **NOT migrated, merged or deployed**.  
**Tracking:** #91 (this work); #89 / PR #90 (owner sessions), #87 / PR #88 (vault primitives), #83 (v0.3 acceptance), #76 (historic independent WebKit test), #81/#84/#86 (unmerged architecture/portability).

## Transfer format (new, separate from v0.3.0 logical-v2 backups)

`examprep-vault-transfer-v1` carries the versioned vault header (master/recovery **wrapped** AES-GCM data key), opaque verifier ID, a sorted list of encrypted vault records, and a separately AES-GCM-authenticated encrypted inventory manifest. The manifest is encrypted using the same in-memory AES-GCM DEK and binds the complete list of opaque record IDs and SHA-256 digests of canonical encrypted record envelopes. The serialized transfer contains **no bank titles, questions, answer keys, certification names, attempt scores, plaintext passphrases, raw DEK or deciphered records**. Opaque IDs, record classes, ciphertext lengths and record counts are observable metadata.

The transfer is **not** encrypted again with the legacy backup passphrase: recovery requires the original high-entropy *vault master* or separate *vault recovery* credential, either of which cryptographically unwraps the existing DEK. Retain both credentials independently in secure offline/password-manager storage. There is **no server password reset** on GitHub Pages.

### Format and validation

- Exact format/version/field checking; canonical sorted unique opaque UUIDs; ciphertext nonce/tag and size checks; exactly one internal `key-check` record whose ID must match the header-associated verifier ID.
- Maximum **64 MiB JSON transfer**, at most 15,001 total encrypted records including the verifier (prototype cap, not yet evidence of production scale). Per-record plaintext cap remains 8 MiB from M2.2-S1.
- Encrypt the independent inventory manifest with AES-GCM authenticated additional data. Its content binds the vault ID, verifier ID, total encrypted record count, and SHA-256 of **every full ciphertext envelope**, including all record IDs, types, nonces and ciphertext. All records are authenticated and decrypted in memory before export or restore; any missing/duplicate/reordered/modified entry, wrong credential, invalid verifier, malformed metadata, unexpected version or integrity mismatch is rejected.
- The backup manifest detects unauthorized **subsets and modified ciphertext** against its authenticated inventory. It does not prevent replay of an entire earlier valid backup nor establish an external timestamp/trusted monotonic state.
- No derived key or plaintext JSON is stored in GitHub, logs, PWA caches, localStorage or in the transfer file. Backups may still be disclosed if a weak master/recovery credential is brute-forced offline.

## Recovery contract

1. Use a completely **empty experimental vault** at a new browser profile/origin on HTTPS, or localhost solely for synthetic CI. Authenticate owner access using an exclusive browser Web Lock before reading/writing.
2. Refuse recovery if the new encrypted database has **any header or records**. Never merge, overwrite, clear or partially replace existing records.
3. Parse a bounded JSON file, validate the strict outer schema, derive the key using the supplied master/recovery credential, authenticate the encrypted manifest and every encrypted record **before the first storage transaction**.
4. Within one short IndexedDB transaction, re-check that both header/record stores are empty and add the header, verifier and *all* ciphertext records. No asynchronous Web Crypto is awaited within a live IDB transaction.
5. Establish an owner session with the cryptographically verified key, then explicitly read back representative bank, attempt, active session and catalog records against the original profile using synthetic fixtures. In later production acceptance, verify **all record types and reference counts**, not only a note.
6. On any parse, crypto, quota, lock or write error, fail closed and preserve preexisting browser data. Browser process crashes during a transaction must be tested; the recovery design depends on IndexedDB atomicity and independently retained external encrypted backups.
7. A restored vault starts with the *same DEK/wrapped key material* as the source. This enables explicit **portable copies**, not automatic synchronization. Concurrent divergence between copies is unsupported and needs a separate conflict/merge design.

## v0.3.0 plaintext IndexedDB migration: DESIGN ONLY, not implemented

The legacy production DB is `examprep-v1` Dexie schema v3 (underlying IndexedDB native version v30). It contains banks, attempts, activeSessions, certifications and syllabusVersions **in plaintext**. The current v0.3.0 logical-v2 encrypted backup includes banks/attempts/catalog but does not include unfinished active sessions.

### Future migration authorization gates

1. **Release acceptance:** resolve #83. Physical macOS Safari, iPhone Safari + Home Screen PWA, and iPadOS Safari + installed PWA (portrait, landscape, Split View, background, keyboard/file picker) are tested. A **post-v0.3.0** logical-v2 backup must be exported and successfully restored to a clean browser profile; verify bank/question/certification/syllabus/attempt counts and score consistency. Resolve historical #76 via trace and repeat-run evidence.
2. **Origin isolation:** stage migration on a dedicated independent hostname/origin, **not** a sibling path on `yenuka2012.github.io`; a repo subpath is not an IndexedDB security boundary. Both GitHub Pages H1 and private HTTPS Ubuntu H2 remain supported, with explicit encrypted export between origins, never implicit sync.
3. **Read-only inventory assessment:** after an explicit owner opt-in, inspect legacy record counts, IDs, schemas, source references, incomplete exams, data sizes and quota. Store only an encrypted report or transient in-memory metrics; no private data in CI logs. If an exam is unfinished, block migration until the owner completes it or a specifically tested encrypted active-session migration exists.
4. **Non-destructive transaction plan:** create a **new encrypted vault** and write validated records using stable logical IDs inside ciphertext and opaque storage UUIDs; use source validation and a resumable journal/progress IDs in encrypted storage. Preserve legacy DB untouched. No unreviewed automatic migration on page load.
5. **Integrity comparison:** decrypt and verify every new record, compare canonical payload and referential integrity to the source; check all bank/attempt/session/catalog types, published syllabus immutability, question snapshots and score calculations.
6. **Independent recovery rehearsal:** export complete encrypted vault (including key verifier, authenticated manifest, all records); restore into a clean browser profile and verify full inventory and representative exam flows. A user-visible success UI is not equivalent to verified recovery.
7. **Explicit destructive cleanup gate:** only after independent recovery, physical-device sign-off, verified backups and separate **owner authorization**, consider removal of *legacy plaintext* IndexedDB. Never clear entire origin/site storage as a substitute. Retain a compatible encrypted recovery build and do not downgrade to v0.2.1/Dexie v2.
8. **Crash and adversarial testing:** interruption after each migration stage, quota exhaustion, browser storage eviction, simultaneous tabs, stale writes, failed Web Locks, tampered records/manifests, corrupt source, incorrect passphrase, lost recovery, and iOS background suspension.

## What is not implemented

Production exam UI integration, live migration, deletion of legacy plaintext, user registration/server authentication, cloud sync, Ubuntu VM deployment, versioned key rotation and trusted anti-rollback state. This PR is a test-only security prototype **even if all automated CI passes**.
