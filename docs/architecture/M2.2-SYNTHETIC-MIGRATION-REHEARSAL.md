# M2.2-S4 — Synthetic encrypted migration rehearsal and crash-safe journaling

**Status:** Candidate in draft PR; synthetic-only engineering work. **Date:** 2026-11-07. **Tracking:** #93, prerequisites #91/#89/#87 and draft PRs #92/#90/#88; release #83, legacy WebKit #76, architecture #81/#84 and hosting #86.

## Explicit non-production boundary

The **only** plaintext source this prototype opens is `examprep-synthetic-legacy-v1`, defined in `src/vault/syntheticLegacy.ts` with five deliberately fake record stores. It never imports `src/db.ts`, never calls the real `examprep-v1` database, never reads an existing question bank, never changes current backup logical-v2 format, never deletes or overwrites plaintext data and never deploys any private test fixture to GitHub Pages. The target is the existing isolated experimental `examprep-secure-vault-v1` database, accessible only after verified owner unlock and exclusive origin-wide Web Lock.

Production browser profiles still have **unencrypted active IndexedDB**; passing synthetic tests cannot be interpreted as production encryption at rest.

## Source snapshot model

The test fixture uses the real *type shapes* of QuestionBank, Attempt, StoredSession, CertificationProfile and SyllabusVersion, with fake CISM-like records and artificial question/answer text. Before copying, the migration validates:

- Exactly five expected store arrays with bounded record count (1–1,000 for this rehearsal).
- Stable, nonempty unique keys per store and per bank question.
- Bank-to-certification, attempt-to-bank/certification, session-to-bank and syllabus-to-certification references.
- Plausible question option/answer references and attempt score bounds.
- A deterministic SHA-256 fingerprint derived from canonical JSON of every source record and its type/key, independent of JavaScript object property insertion order.

The source DB snapshot is read within one IndexedDB read transaction and reread at the end. A changed source fingerprint, malformed/missing source reference, stale journal or corrupted ciphertext **blocks validation**; no automated repair, plaintext cleanup or force-resume occurs.

## Encrypted journal and interruption policy

`migration-journal` is a reserved, versioned AES-GCM record class held **inside the experimental vault**; it is not an unencrypted localStorage or IndexedDB metadata index. The journal contains the source fingerprint, the bounded list of logical source keys, SHA-256 payload digests, generated destination UUIDs and per-entry `copied` state, all encrypted under the owner vault DEK.

1. Owner explicitly seeds the test-only fixture and starts the rehearsal.
2. Under the unlocked owner session, the engine captures and validates the read-consistent source snapshot and calculates the inventory fingerprint.
3. A journal of every planned source-to-destination UUID is **encrypted and durably stored before copying the first payload**.
4. For each entry, the engine reads the fixed destination UUID. If no ciphertext exists and the entry was only planned, it encrypts the source payload under that ID and verifies it by decrypting/rehashing immediately. It never silently creates a new ID during retry.
5. If an interruption occurs **after** the destination write but **before** the journal checkpoint, a retry sees the already written UUID, authenticates it and compares its entire payload digest, then safely checkpoints. This avoids duplicate encrypted records or replaying a stale update.
6. Every journal checkpoint is a nonce-based compare-and-swap encrypted record write. The source data, logical source ID and destination UUID must be consistent; mismatch halts instead of overwriting another record.
7. On final validation, all five destination classes are re-decrypted/compared against the original snapshot, and the source is reread and fingerprinted again. Only then is the encrypted journal marked `validated`. A final journal read-back confirms the committed completion state.
8. The completion record is **local copy verified**, not a claim that another device can recover, that active exams are fully compatible, or that plaintext data may be deleted.

### Safety properties and limits

- **No source deletion or mutation.** Repeated valid migration is idempotent. A source mutation, missing ciphertext that the journal claims was copied, changed record identity, bad authentication tag or journal tamper blocks completion.
- **No raw DEK or user passphrase persisted.** Destination records and journal are AES-GCM authenticated; only permitted record-type labels and opaque identifiers appear outside ciphertext. Test-only source DB is intentionally plaintext within its separate local harness origin.
- **Crash simulation** currently exercises a persisted encrypted write **before** its journal checkpoint followed by browser reload/unlock/resume. This does not simulate an OS power loss, filesystem corruption or every possible IndexedDB crash boundary; those are future acceptance tests.
- **No live source concurrent-writer control** is implemented. Future production migration must take a read-consistent snapshot **and prevent writes from the existing live app**, or use a verified source revision/snapshot journal. Merely owning a lock in the new experimental vault does not serialize legacy app writers.
- A browser storage eviction can remove both target ciphertext and journal. Independent encrypted export/restore is required before touching owner data. Entire-old-snapshot rollback cannot be detected without external trusted state; see ADR-002.
- An in-progress **real** active examination requires explicit recovery policy before migration. The S4 fixture includes a synthetic active session solely to exercise all five record categories.

## Clean-profile recovery rehearsal

After a successful synthetic migration, the owner session exports the existing **M2.2-S3** `examprep-vault-transfer-v1` ciphertext-only backup, including the encrypted journal, all five copied data records, and the key verifier. A separate clean-browser-profile session restores it with the independent recovery credential, then verifies every migrated record against the authenticated journal and its source hash. The original synthetic source DB remains untouched and is not needed by the restored profile.
