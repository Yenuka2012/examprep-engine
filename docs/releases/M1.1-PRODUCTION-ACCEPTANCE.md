## Critical compatibility boundary
1. **Database**: The M1.1 app upgrades `examprep-v1` from Dexie v2 / native IndexedDB v20 to Dexie v3 / native IndexedDB v30, adding catalog stores. The deployed v0.2.1 application targets v20 and cannot safely open the upgraded database; it should fail with `VersionError` rather than delete data.
2. **Logical backup**: The `backup_version` inside the authenticated payload is **2** for new backups and requires `certifications` and `syllabi` arrays. The old app rejects it by version. The M1.1 app accepts both logical v1 and v2; logical v1 cannot carry catalog metadata. Legacy plaintext v1 requires explicit warning; plaintext v2 is rejected.
3. **Crypto envelope**: `format: examprep-encrypted-backup-v1`, AES-256-GCM, and PBKDF2-SHA256 remain unchanged. Do not confuse envelope version with inner logical data version.

## Incident rollback (data-preserving)
1. **Do not** delete IndexedDB, local browser profile or Cache Storage and do not attempt a destructive v3→v2 schema downgrade.
2. Suspend further upgrades. Capture failing app version, last good SHA, browser version, logs and non-private diagnostics.
3. A direct static-site rollback to v0.2.1 is **not safe for upgraded profiles**, because their IDB is version 30. Treat the v0.2.1 build as a last-resort static fallback only for *unmigrated* profiles.
4. Prepare an emergency hotfix from v0.3.0 retaining the **Dexie v3 schema, logical backup v2 reader and all existing stores**. Disable offending catalog UI/features in the hotfix if required; never drop tables. Validate recovery using synthetic migrated v3 data, then deploy through protected CI.
5. If irrecoverable, assist an affected user on a compatible v0.3.0+ recovery build using their pre-upgrade v1 encrypted backup (loses any post-backup work unless a newer v2 backup exists). Clearly communicate possible data loss before taking action.
6. Document incident, root cause, resolution and release evidence against #31, #49 and #78.
